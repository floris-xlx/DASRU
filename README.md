# DASRU

DOOM: The Dark Ages SpeedRun Utility. Includes a read-only Windows x64 identity probe and an optional native desktop interface.

On Windows, run `cargo run --locked --features desktop-ui --bin dasru-gui` (Rust 1.95 or newer). The compact two-column desktop shows real process/build and hotkey status in one fixed-width utility window, with separate Settings, Help and Diagnostics dialogs. It controls a read-only observation shortcut, exports privacy-safe support reports, and stores validated UI preferences. It does not enable gameplay actions. See [desktop architecture](docs/gui-architecture.md) and [acceptance evidence](docs/pr10-tdd-evidence.md); the desktop remains a draft pending live acceptance.

```text
dasru doctor
dasru doctor --json
dasru probe
dasru probe --json
dasru support export support-report.json
dasru inspect --exe "C:\path\to\DOOMTheDarkAges.exe"
dasru inspect --exe "C:\path\to\DOOMTheDarkAges.exe" --json
dasru memory scan --metrics
dasru memory scan --metrics --json
dasru memory inspect --metrics
dasru memory inspect --metrics --json
dasru memory inspect --metrics --replacement "%i FPS+" --json
dasru memory discover --metrics-objects --json
```

`doctor` emits a support report with host OS/version, architecture, Linux distribution/kernel and session type (`X11`, `WAYLAND`, or `HEADLESS`). `xwayland_available` reports XWayland separately for Linux Wayland sessions. It also reports Steam/Proton/Wine environment signals and host capability hints. JSON uses `schema_version: 1`. Runtime detection reports environment variable names only, never their values. Capability and feature records keep `detected`, `accessible`, and `implementation_status` separate. `UNKNOWN` means no access test was run; a detected clipboard utility or display session never marks clipboard or hotkeys as available. The Wayland GlobalShortcuts portal is reported as `UNKNOWN` because doctor does not query D-Bus. Doctor does not register hotkeys. Doctor exits `0` when it emits a report and `2` for invalid CLI usage.

`support export <path>` writes a versioned JSON support bundle containing host diagnostics, input capability hints, executable/build compatibility status, and structured error codes. It stages beside the destination and publishes without overwriting an existing file. Unix reports use mode `0600`; Windows reports are created in the destination directory and inherit its access controls. That ACL behavior can vary with filesystem and filter-driver policy and is not verified for every Windows filesystem. The destination filesystem must support hard links; a filesystem that does not support them returns `SUPPORT_EXPORT_PUBLISH_FAILED` and leaves no destination file. Unix and Windows CI exercise their respective local filesystems, not every destination filesystem. The bundle includes environment variable names and the inspected executable SHA-256 for compatibility checks, but omits environment values, executable and Steam install paths, PIDs, raw process lists, and raw error messages. `keyboard_input` remains `NOT_IMPLEMENTED`. `global_hotkeys` is implemented on Windows and reports readiness only while the Raw Input listener is active for a verified registered TDA build in the foreground. Export exits `0` on success, `1` for collection or publication failure, and `2` for invalid CLI usage.

`hotkeys listen --bind CTRL+ALT+F9` starts a read-only Windows hotkey listener. Bindings must include Ctrl, Alt, or Shift; bare keys, Windows-key combinations, F12, known reserved shortcuts, invalid virtual keys, and duplicates are rejected. The listener receives Raw Input keyboard events on a dedicated hidden window, tracks only modifiers and configured binding keys, and dispatches a chord only after revalidating the pinned TDA identity and current foreground PID. It does not reserve the chord system-wide, synthesize input, or execute game actions. It requires exactly one accessible TDA process whose executable matches a registered build. Raw Input registration is active only while TDA is verified and foregrounded; focus loss removes it, clears tracked state, and discards queued key messages. Each captured event carries a focus generation; events from an earlier generation are discarded before dispatch and before accepted/rejected event output. Shutdown removes any remaining Raw Input registration and the foreground notification hook, then prints saturating `HOTKEY_DIAGNOSTICS` counters for observed, forwarded, discarded, processed, accepted, rejected, identity, focus, and lifecycle stages. The counters contain no key codes or process identities. A focus transition can still race with queued input, so physical delivery and restart behavior remain subject to the live Windows acceptance checklist in `docs/pr8-tdd-evidence.md`.

`inspect --exe` hashes and reads version metadata from an executable without looking for a running process. Its report uses `PROCESS_NOT_EVALUATED` semantics (`process_status: NOT_EVALUATED`), with an empty process list. `probe` discovers a process by executable name, retains its Windows process handle while it hashes the executable, and reports the live process identity.

JSON reports use `schema_version: 1`; `observed_at_unix_ms` is the UTC Unix epoch time in milliseconds. `status` reports the overall executable/process result. `executable_status` and `steam_status` keep executable recognition separate from Steam metadata. The Steam manifest is checked for App ID, `installdir`, and Build ID format; its resolved install directory must contain the inspected executable. A registered Steam Build ID is compared separately, so a mismatch does not erase a known executable hash. Field provenance and structured errors identify the evidence source and failed field. `run_integrity` remains `NOT_EVALUATED`.

CLI exit codes are stable: `0` means executable inspection completed with either an exact or unknown build; `1` means a process/probe or executable inspection failure; `2` means invalid CLI usage. Exit `0` does not mean Steam metadata succeeded or that run integrity was evaluated: check `steam_status`, `errors`, and `run_integrity` separately.

The registry includes the verified Steam build 25755602 fingerprint. Build compatibility does not establish run integrity, and neither the local registry nor its report is a tamper-proof attestation. Linux process discovery and game-memory access are not implemented.

`memory scan --metrics` scans the main module of the single verified process for the shared FPS format signature. It requests `PROCESS_QUERY_INFORMATION` and `PROCESS_VM_READ` only, walks committed readable regions with `VirtualQueryEx`, and reads them with `ReadProcessMemory`. Guarded, inaccessible, and uncommitted regions are skipped and counted. The report includes every match with its absolute and module-relative address, memory region type, and protection. `bytes_read` counts bytes returned by Windows, `bytes_scanned` counts bytes accepted as complete evidence, `bytes_untrusted` counts returned bytes from failed reads that were excluded, and `bytes_unreadable` counts missing or skipped bytes. `coverage` is `FULL_MODULE` only when every module byte was scanned successfully; otherwise the status is `PARTIAL_SCAN`, with any observed matches retained. A unique match is reported only after complete coverage; ambiguous matches and process/scan errors return exit code `1`. Failed or short reads do not contribute bytes to signature matches.

`memory inspect --metrics` performs the same complete, read-only scan, then reads a bounded context around one unique match. It reports the exact context bytes, region type and protection, the starts and terminators of the three format strings, and conservative byte capacities. Its dry-run defaults to `%i FPS*`; `--replacement` accepts an ASCII candidate that preserves the `%i FPS` prefix, such as `%i FPS+` (`--fps-label` remains an alias). It reports actual changed bytes separately from the bounded patch span, and accepts a candidate only when its complete text and NUL terminator fit inside the first string's slot. `SAFE` means only that the byte plan stays within the observed slot; it does not authorize or perform a write. `UNSUPPORTED` means the layout or replacement cannot be established safely, and `AMBIGUOUS` means multiple process or signature candidates were found. A completed unique scan exits `0` even when the replacement is unsupported; incomplete scans and process errors exit `1`. This command never writes to game memory; run integrity remains `NOT_EVALUATED`.

`memory discover --metrics-objects --json` performs read-only live discovery of candidate metrics-owner objects. The current offsets are enabled only for the registered `steam-25755602` executable SHA-256; another recognized build returns `UNSUPPORTED_LAYOUT` before memory scanning. The report records scan coverage independently from candidate-validation and sampling status. It reads up to 256 bytes from each row target and up to 64 bytes from readable nested-pointer targets, stopping at each readable region boundary. It reports bounded ASCII runs, separately marks a leading NUL-terminated ASCII candidate, address-shaped values, readable nested targets, and five timestamped samples 250 ms apart. Changed aligned 4-byte words include raw little-endian `u32` and finite `f32` views; those views do not identify a field's meaning. `expected_label_matches` and `direct_label_matches` count direct target strings; `nested_label_matches` counts labels reached through a nested pointer. Only valid row pointers and direct label matches affect structural confidence. For non-string rows it reads the `+0x88` history pointer, `+0x90` count and `+0x94` capacity. It rejects `count > capacity`, capacities above 256 elements, invalid pointers and address overflow; before reading `count * 0x48` bytes it validates the declared `capacity * 0x48` span across committed readable regions with one `VirtualQueryEx` allocation base. This checks virtual allocation bounds; Windows does not expose the heap block size here. Raw element bytes and changed aligned-word views carry no inferred field meanings. Each sample rechecks the process identity and row pointer, and reports data-pointer, count, capacity, element changes and read errors separately. `static_render_slot_reads` records disassembled loads for all eight owner slots. Build-gated `static_data_flow` records the static template-to-stack-buffer-to-glyph-batch path, while marking the row-history-to-text link, runtime invocation and final GPU submission as unestablished or unobserved. `AMBIGUOUS_CANDIDATE` can coexist with `coverage: PARTIAL`; then the observed candidates are not exhaustive. This command never writes to game memory.
